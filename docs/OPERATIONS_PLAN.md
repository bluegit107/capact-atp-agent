# capact 운영 전환 기획서

> 대형 수주와 기존 고객 약속을 함께 판단하는 업무 도구 capact 를, 대회 시연본에서 실제 사내 운영으로 옮기기 위한 설계와 계획.
> 구분 표기: **[구현됨]** 지금 코드에서 동작하고 시험으로 확인함 / **[모의]** 같은 인터페이스의 대역으로 동작 / **[계획]** 설계만.
> 원칙은 하나다. **업무 규칙(권한표, 가정 대장, 변경 전파, 결정론 계산)은 그대로 두고 바깥 연결만 바꾼다.** 처음부터 포트와 어댑터로 나눈 이유다.

## 목차
1. 지금 구조 한눈에
2. 에이전트 시스템과 가드레일
3. 데이터 연계와 확장(생산 라인, 제품, 거래처 추가)
4. 사내 시스템 연계(메일, 메신저, ERP/MES, 인증)
5. 다중 접속과 온프레미스 전환
6. 보안과 감사
7. 도메인 확장 계획(현업 검토에서 나올 지적)
8. 단계별 실행 계획과 완료 기준

## 1. 지금 구조 한눈에

```
원본 데이터(읽기 전용, 해시 고정)
   └─ 도출 스크립트 ─▶ 입력 파일(JSON 계약)  ◀── 운영에서는 ERP/MES 커넥터가 이 자리를 대신함
                           │
         ┌─────────────────┼──────────────────────┐
     계산 엔진(결정론)   업무 흐름(상태 기계)     에이전트(설명, 의견, 초안)
     라인×주 ATP 원장     가정 대장, 승인, 작업,   도구 15개, 숫자 검증기,
     충족률, 손익, 위험    생산 예약, 변경 전파      호출 한도, 녹화 재생
                           │
                    FastAPI + 역할별 화면 ── PostgreSQL(앱 단 암호화), 감사 기록
```

| 층 | 지금 | 운영 |
|---|---|---|
| 계산 | [구현됨] 라인×주 원장, 충족률, 손익 9칸(단가 인하×환율 하락), 위험 표시 10종 | 그대로 |
| 업무 흐름 | [구현됨] 접수 → 확인 대기 → 검토 → 상신 → 승인 → 제출 준비 → 제출, 예외: 보류 | 그대로, 입찰 건을 여러 개로 |
| AI | [구현됨] 실제 모델 연결(로컬 시연) / [모의] 규칙 모델(배포본 기본값) | 사내 승인된 모델 엔드포인트 |
| 데이터 | [모의] 원본에서 도출한 파일 | [계획] ERP/MES 커넥터 |
| 외부 회신, 발송 | [모의] 시연 진행자 입력, 외부 수신함 기록 | [계획] 메일, 메신저 어댑터 |
| 인증 | [구현됨] 부서 단위 계정, 비밀번호 해시, 세션 | [계획] 개인 계정, 사내 SSO |

## 2. 에이전트 시스템과 가드레일

### 2.1 역할 분담: 계산은 엔진, 판단은 사람, 설명은 AI
| 하는 일 | 누가 |
|---|---|
| 원장, 충족률, 손익, 대안 구성, 가능/조건부/불가 판정, 위험 표시 판정 | 계산 엔진(결정론, 같은 입력이면 같은 결과) |
| 상황 요약, 대안과 위험 설명, 선호 의견, 변경 영향 요약, 확인요청 문구 다듬기, 빠진 정보를 "미확인 가정"으로 제안 | AI |
| 확인요청 발송, 회신을 가정으로 확인, 상신, 승인, 생산 예약 확정, 원료 회신 | 사람(권한표의 역할) |

### 2.2 실행 방식 [구현됨]
- **계기 사건마다 한 번 실행**: RFP 접수, 회신 반영, 가정 교체, 승인 결정(승인 외), 마감 임박. 결과는 "제안"으로만 남고 업무 상태를 바꾸지 않는다.
- **수동 도구 루프**: 서버가 도구를 직접 실행한다. 도구 15개 = 조회 10(입찰 사진, 가정 목록, RFP, 기존 약속, 고객 추이, 라인 능력, 설비안, 원료 계약, 클레임, 위험 표시) + 쓰기 제안 4(미확인 가정 등록, 확인요청 문구, 대안 설명, 위험 설명) + 종료 1.
- **한도**: 도구 호출 12회, 60초. 결과 검증 실패 시 1회 재시도, 그래도 실패하면 "사람 확인 필요" 작업을 영업에게 만들고 업무는 계속 진행(AI 장애가 업무를 멈추지 않음).
- **녹화와 재생**: 실제 모델 실행을 기록하고, 키 없이 같은 결과를 재생한다. 재생 중 도구 결과가 달라지면 불일치로 멈춘다(재현성 검증).
- **모델 교체**: 환경변수만 바꾼다(`AGENT_MODE=mock|live|replay`, 모델명, 엔드포인트). 실제 연결은 OpenRouter 경유로 시연했고, Anthropic 직접 연결은 같은 요청 형식을 대역 클라이언트로 시험했다.

### 2.3 가드레일 목록
| 번호 | 규칙 | 강제 위치 | 상태 |
|---|---|---|---|
| G1 | 결정(승인, 거절)은 권한표의 권한자만. AI 도구 목록에 승인, 확정, 발송, 작업 완료가 아예 없음 | 업무 흐름, 도구 목록 | [구현됨] |
| G2 | AI 문장에 숫자를 직접 쓰지 못함. 계산 결과는 `{{calc:id}}`, 가정은 `{{assume:id}}` 자리표시자로만. 서버가 값으로 치환 | 숫자 검증기(코드명과 한국어 조사 구분 포함) | [구현됨] |
| G5 | 핵심 가정(납품 개시일, 부분 물량 허용)이 미확인이면 상신 불가 | 업무 흐름 | [구현됨] |
| G7 | C-101 수주 감소분은 영업 임원이 확정하기 전에는 여력으로 쓰지 않음 | 계산 엔진 | [구현됨] |
| G10 | 마감 7일 전 독촉 작업, 마감 경과 시 참여 보류와 열린 작업 취소 | 업무 흐름(시계) | [구현됨] |
| G11 | AI 실패가 업무를 막지 않음. 공백 탐지와 대안 구성은 규칙으로도 같은 결과 | 실행 루프 | [구현됨] |
| G12 | 외부 문장(회신, 통지, 원본 문서)은 자료일 뿐 지시가 아님. 사람이 "가정 확인", "가정 교체"를 눌러야 반영 | 업무 흐름, 시스템 프롬프트 | [구현됨] |
| G13 | 계산을 거친 대안만 제시. AI는 대안을 만들지 않음 | 대안 구성 규칙 | [구현됨] |
| G15 | 차단(BLOCK) 위험 표시가 남은 대안은 상신 불가 | 업무 흐름 | [구현됨] |
| G16 | 역할별로 볼 수 없는 값은 응답에서 제거. AI 설명은 그 위험 표시의 근거 계산만 인용 가능 | 화면 데이터 조립, 도구 계층 | [구현됨] |

**경계 사례 시험**: 정보 없음, 마감 독촉과 보류, 차단 대안, 구매 재계약 거절, 설비투자 거절, 입찰 참여 거절, 납품 극단 앞당김, 부분 물량 불허 등 9가지에서 AI가 불가하거나 막힌 대안을 추천하지 않음을 시험으로 확인.

### 2.4 운영 전환 때 더할 가드레일 [계획]
- **프롬프트 주입 방어 강화**: 메일 본문을 AI에 넘기기 전 지시문 패턴 탐지, 본문은 항상 "자료" 구획에만 넣는 현 방식을 유지하고 모델 출력이 도구 인자로 외부 주소를 만들지 못하게 화이트리스트.
- **비용과 지연 한도**: 입찰 건별 일일 호출 수, 토큰 상한, 모델 장애 시 규칙 모델로 자동 대체.
- **품질 감시**: 숫자 검증 실패율, 사람 확인 작업 발생률, 추천과 실제 승인 대안의 일치율을 주간 지표로.
- **모델 버전 고정**: 모델 교체 시 녹화된 사건들로 재생 비교 후 승격.

## 3. 데이터 연계와 확장

### 3.1 데이터 층과 교체 지점
| 층 | 내용 | 다른 데이터에서 | 상태 |
|---|---|---|---|
| 원본 | 수주, 출하, 생산 배치, 라인 용량, 설비안, 원료 계약, 클레임, 환율, RFP, 권한표 | 같은 열 구조면 그대로 | [구현됨] |
| 도출 | 기존 약속(77일 이내 미출하), 상태 불명 주문, 라인 능력(상반기 생산량÷26주÷가동률), 재료비, 결함률 | 스크립트 재실행 | [구현됨] |
| 입력 계약 | 하나의 JSON. 모든 행에 원본 행 번호 유지(근거 드로어가 원본 행까지 추적) | **ERP/MES 커넥터가 같은 형식으로 생성** | [계획] |
| 엔진 | 라인, 제품, 설비안, 거래처, 기준일을 데이터에서 읽음 | 코드 수정 없음 | [구현됨] |
| 아직 고정 | 입찰 1건 단위, 외부 상대(바이어, 원료 공급사), C-101 전용 수요 규칙, 위험 규칙 문구 | 코드 수정 필요 → 3.3 | [계획] |

### 3.2 생산 라인이 늘면 실제로 되는가 [구현됨, 시험으로 확인]
- 라인, 제품, 설비안을 코드 상수가 아니라 데이터의 구성(topology)에서 읽는다.
- 시험(`test_w05_extensibility.py`)으로 다음을 데이터만 추가해 확인: F3 공장 신설 라인, 새 제품, 기존 라인 증설안, 새 전환안, 새 고객. 원장, 대안 구성, 위험 표시, 보드, 홈 화면까지 코드 수정 없이 끝까지 동작.
- 새 설비안의 선행 요건(원료 재계약, 처방 재검증)은 설비안 비고 문구에서 규칙으로 도출("불필요" 같은 부정 표현 구분). 요건이 있으면 핵심 가정, 담당 부서 확인요청, 상신 차단 표시가 같은 규칙으로 자동 생성.
- 기준일(원장 시작 주, 제출 마감, 설비 결정일)도 데이터의 기준일과 달력 설정에서 계산. 다른 시점의 데이터셋을 넣으면 함께 움직임(시험 포함).

### 3.3 실무 적용을 위해 남은 데이터 작업 [계획]
| 작업 | 내용 |
|---|---|
| 입찰 여러 건 | 입찰 건을 저장소의 행 단위로 분리, 건별 화면과 권한. 라인 여력은 건 사이에서 예약으로 공유(먼저 확정한 건이 여력을 가져감) |
| 외부 상대 데이터화 | 바이어, 공급사를 거래처 마스터에서 읽고 확인요청 대상도 규칙표로 |
| 규칙표 데이터화 | 위험 표시 규칙, 승인 생성 규칙(어떤 결정에 어떤 승인이 필요한지), 고객별 수요 규칙을 정책관리자가 관리하는 표로. 지금 권한표처럼 버전과 변경 사유 기록 |
| 데이터 신선도 | 커넥터가 언제 갱신했는지 화면에 표시, 오래되면 상신 경고 |
| 단위와 기준 확인 | 용량표 단위처럼 원본이 모호한 값은 "도출" 배지와 담당 부서 확인요청을 자동으로 |

## 4. 사내 시스템 연계

| 연계 | 지금 | 계획 | 안전장치 |
|---|---|---|---|
| **사내 메일** | [모의] 확인요청 발송을 외부 수신함에 기록, 회신은 시연 진행자가 입력 | 확인요청 발송 = 메일 어댑터가 담당자에게 발송(회신 기한, 고유 번호 포함). 회신 메일을 수신함에서 읽어 확인요청에 연결. AI가 회신 문장을 구조화(날짜, 가능 여부, 조건)해 **초안**으로 보여 주고 사람이 "가정 확인" | 외부 문장은 지시가 아님(G12). 첨부와 링크는 열지 않고 자료로만 |
| **사내 메신저** | 없음 | 내 할 일, 마감 독촉, 승인 요청을 메신저 알림으로. 버튼은 앱으로 이동만(메신저에서 승인 금지, 권한 확인은 앱에서) | 결정은 항상 앱의 권한 검사 경로 |
| **ERP(수주, 출하, 재무)** | [모의] 원본 도출 파일 | 매일 배치 또는 변경 이벤트로 입력 계약(JSON) 생성. 원본 행 번호 대신 ERP 문서 번호 유지 | 읽기 전용 계정, 커넥터 실패 시 마지막 성공본과 갱신 시각 표시 |
| **MES(배치, 가동률)** | [모의] 원본 도출 파일 | 주 단위 생산 실적 집계 커넥터. 라인 추가는 데이터 행 추가로 끝 | 같은 계약, 같은 시험 |
| **구매, 품질 시스템** | [모의] 부서 담당자가 앱에서 회신 | 재계약, 재검증 상태를 확인요청 자동 회신으로 | 자동 회신도 가정 확인은 사람 |
| **그룹 상신, 입찰 제출** | [모의] 상태 전이와 발송 기록 | 전자결재 연동(상신 요약을 결재 문서로), 제출 패키지 생성 | 결재 결과가 돌아와야 상태 전이 |
| **인증** | [구현됨] 부서 단위 계정 10개 | 사내 SSO(OIDC 또는 SAML). 인사 조직에서 역할 매핑, 한 사람 여러 역할, 부재 시 대리 지정과 기간 | 권한표는 그대로, 사용자만 개인으로 |

**확인요청과 작업 담당을 개인으로**: 지금은 역할(예: 구매)에게 가는 확인요청과 작업을 개인 담당자와 대리인에게 지정. 승인 기록에도 개인 이름을 남긴다(감사 기록은 이미 실제 사용자와 대리 역할을 함께 기록).

## 5. 다중 접속과 온프레미스 전환

### 5.1 지금 [구현됨]
- 동시 수정: 낙관적 잠금(버전 번호). 다른 사람이 먼저 저장하면 409와 새로고침 안내.
- 세션: DB 저장(토큰 해시). 여러 인스턴스가 공유 가능한 형태.
- 계산: 프로세스 안 동시 2건 제한, 결과 캐시(입찰 건 버전이 키라 오래된 결과를 쓰지 않음).
- 실측: 0.5코어 서버에서 화면 응답 0.1~0.2초, 계산 약 1초.
- 알려진 한계: 실제 모델 호출(10~25초) 동안 요청이 열려 있어, 그 사이 같은 입찰 건의 다른 쓰기가 겹치면 409가 난다.

### 5.2 운영 구조 [계획]
```
사용자 ─ 사내 SSO ─ 부하 분산 ─┬─ 앱 인스턴스 N개(무상태)
                                │      ├─ PostgreSQL(주) + 읽기 복제본
                                │      └─ 공유 캐시(버전 키)
                                ├─ 작업 큐 ─ 계산 워커, AI 워커(비동기)
                                ├─ 스케줄러 1개(마감 시계, 커넥터 갱신)
                                └─ 메일/메신저 어댑터, ERP/MES 커넥터
```
| 영역 | 변경 | 이유 |
|---|---|---|
| AI 실행 | 요청 안에서 기다리지 않고 작업 큐로. 끝나면 화면에 서버 전송 이벤트(SSE)로 알림 | 위 409 문제 해소, 응답 지연 제거 |
| 계산 | 별도 워커, 입찰 건 버전 키 캐시를 공유 저장소로 | 인스턴스 수와 무관하게 같은 결과 재사용 |
| 동시 편집 | 낙관적 잠금 유지 + 입찰 건 단위 행 분리 + "다른 사람이 가정을 바꿨습니다" 실시간 알림 | 충돌 범위를 건 하나로 줄임 |
| 시계, 마감 | 단일 스케줄러 작업(중복 실행 방지 잠금) | 독촉, 보류가 두 번 일어나지 않게 |
| 관측 | 요청 지연, 계산 시간, AI 실패율, 숫자 검증 실패율, 큐 길이 지표와 경보 | 운영 이상 조기 발견 |

### 5.3 온프레미스 전환 [계획]
- **배포 단위**: 지금의 컨테이너 이미지 그대로(앱, 워커, 스케줄러는 실행 명령만 다름). 사내 쿠버네티스 또는 VM의 컨테이너 런타임.
- **외부 의존 제거**: 글꼴은 이미 자체 호스팅, 외부 CDN 없음(CSP로 차단). AI 엔드포인트만 외부이므로 사내 승인 모델 게이트웨이로 교체(엔드포인트 환경변수 하나).
- **비밀값**: API 키, DB 접속, 암호화 키는 사내 비밀 저장소에서 주입. 저장소에 두지 않는다(지금도 동일).
- **DB**: 사내 PostgreSQL. 앱 단 AES-GCM 암호화 유지, 키 교체 절차와 백업 복구 훈련.
- **망 분리 환경**: AI 없이도 업무가 돈다(G11). 모델 접근이 막히면 규칙 모델로 자동 대체되어 계산과 업무 흐름은 그대로.

## 6. 보안과 감사 [구현됨, 운영에서 유지]
- 비밀번호 scrypt 해시, DB 세션(토큰 해시), CSRF 헤더 검사, CSP와 보안 헤더, 로그인 5회 실패 시 10분 잠금.
- 권한표 하나로 서버 검사와 화면 버튼을 함께 결정(화면만 숨기는 방식이 아님). 권한표 변경은 정책관리자만, 버전과 사유 기록. 진행 중 승인은 요청 시점 버전을 따름.
- 역할별 열람: 생산, 구매에는 단가와 손익을 응답에서 제거. 재무 위험은 재무와 CEO만.
- 감사 기록은 추가 전용. 실제 사용자와 대리 역할, 원인 사건을 함께 기록. 시험 초기화도 삭제가 아니라 새 회차.
- 시연 도구(모의 회신, 가상 시계, 초기화)는 시연 진행자만, 운영에서는 환경변수로 꺼짐(서버가 404).
- 원본 데이터는 읽기 전용, 파일 해시 변경 시 시험 실패.

## 7. 도메인 확장 계획

현업 검토에서 나올 지적과 현재 처리, 다음 단계. 모두 "데이터나 규칙 추가"로 넣을 수 있게 자리를 잡아 두었다.

| 분야 | 지적 | 지금 | 다음 단계 |
|---|---|---|---|
| 생산 | 남는 주에 미리 만들어 재고로 쌓으면? | 주별 여력을 이월하지 않음(보수적) | "선행 생산" 레버. 사용기한, 창고 용량 확인요청과 함께 |
| 생산 | 증설 직후 100% 능력? | 준비 주부터 추가 능력 전부 | 설비안 데이터에 램프업 곡선 열 추가 |
| 생산 | 특근, 교대 | 원장에는 없음, 협상 분석 화면에서 한계선 계산 | 근무형태 데이터 연계 후 원장 제약으로 |
| 생산 | 품질 보류 배치, 라인 전환 손실 | 위험 표시로만 | 보류 수량을 여력에서 차감하는 규칙 |
| 영업 | 물량과 단가를 묶어 협상 | 대안은 규칙으로 생성, 단가 영향은 손익 9칸 | 물량 슬라이더를 원장에 직접 연결(계산은 결정론 유지) |
| 영업 | 여러 입찰 동시 관리 | 1건 | 3.3의 입찰 여러 건 |
| 영업 | C-101 감소 원인 | 확인 대상 표시, 반영은 영업 임원(G7) | CRM 연계 |
| 구매 | 원료 주별 공급 한도 | 재계약 여부를 관문으로만 | 원료 공급량을 원장의 두 번째 제약으로 |
| 재무 | 재료비만 빼면 이익 과대 | "재료비 차감 이익"으로 명시 | 가공비, 감가상각, 운전자본, NPV |
| 재무 | 환율 헤지 | 환율 하락 시나리오 | 재무 회신 항목으로 |
| 품질 | 리콜 비용 공급자 부담 | 확정 결함률로 기대비용, 위험 표시 | 품질 회신으로 결함률 가정 갱신 |

## 8. 단계별 실행 계획과 완료 기준

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1. 개인 계정 | 사내 SSO, 역할 매핑, 확인요청과 작업 담당을 개인으로, 대리 지정 | 부서 공용 계정 0개, 감사 기록이 개인 단위 |
| 2. 데이터 커넥터 | ERP, MES 읽기 전용 커넥터가 입력 계약 생성 | 원본 파일 없이 같은 시험 통과, 근거 드로어가 ERP 문서 번호까지 |
| 3. 실제 모델 상시화 | 사내 승인 모델 엔드포인트, 녹화 재생으로 승격 검증 | 숫자 검증 실패율과 사람 확인 발생률 기준치 이하 |
| 4. 메일, 메신저 | 확인요청 발송과 회신 수신, 알림 | 회신이 가정 확인 초안으로 연결, 결정은 앱에서만 |
| 5. 다중 접속 | 작업 큐, 공유 캐시, 다중 인스턴스, 스케줄러, SSE | 동시 사용 부하 시험에서 409는 실제 충돌일 때만 |
| 6. 입찰 여러 건 | 건 단위 저장, 라인 여력 공유 예약 | 두 건이 같은 주 여력을 이중으로 약속하지 않음 |
| 7. 도메인 확장 | 7장의 선행 생산, 램프업, 원료 공급 한도, 원가 확장 | 각 항목에 시험과 근거 드로어 연결 |

각 단계의 회귀 기준: 현재 시험 272건과 업무 지시서 기대값(충족률, 손익, 위험 규칙) 재현이 계속 통과할 것.
